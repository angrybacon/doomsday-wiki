#+AUTHOR: Mathieu Marques

** Preamble

Contributions are more than welcome, thank you for considering it!

Pull requests work best. Below are guidelines set to help you in the process of
providing reviewable work.

** Contributing with Code

We're all consenting adults, use history as documentation and as long as you
respect the existing conventions and configured linting tools you can't go very
wrong.

** Contributing with Content

In an effort to avoid repeating myself and having to maintain things in multiple
places, the Markdown conventions guidelines and supported features will live
next to the code. Visit =/markdown= anywhere the Wiki is hosted to access the
guidelines.

*** File Structure

Content consists of chapters and articles under =markdown/=. The chapters are
considered /timeless/ and are the content that should be kept up to date to
account for meta shifts, bannings and new printings. Articles on the other hand
are dated content.

- =articles/= ::
  Dated reports, primers and theories.
- =chapters/= ::
  Most of the educational content goes there, organized in archetype chapters.
  There's also =chapters/appendices/= for general-purpose resources.
- =partials/= ::
  Static content within the Wiki comes from those partials, this avoids having
  to maintain content within code.

*** Tables of Content

An automatic table of content will be created for all chapters and articles.
Nothing to do on your side! The table will look for level 2 and 3 headings in
the whole document and render itself as a list of anchor links.

Mana symbols and card names are not officially supported in headings. The
heading slugs will look strange if you use markup so prefer simpler titles.

*** Capitalization of Names

Some card names and keyword mechanics double as ordinary English words (e.g.
/Oracle/ for /Thassa's Oracle/, /Storm/ as a keyword mechanic). Here are a
number of heuristics to follow.

- ="Oracle"= used as the card's name ::
  Capitalized. Used as /the/ name, even with an ordinal or modifying another
  noun (e.g. "cast Oracle", "the second Oracle", "the Oracle trigger", "an
  Oracle pile"). Swapping in "it" or "this card" would not work here.
- ="oracle"= generic reference to the card ::
  Lowercased. Generic reference to the card as an object (e.g. "they remove the
  oracle", "to pitch an oracle to a Force", "the oracle's trigger"). Reword to
  add "the" or "an" where it reads better than the bare capitalized form
  described above.
- ="Storm"= keywords that share a name with an archetype or common word ::
  Capitalized. To be italicized in addition to disambiguate from the archetype
  name (e.g. "generate lethal /Storm/", "the Storm archetype"). Never italicize
  inside headings.
- ="storm"= used as a verb ::
  Lowercased. Common slang verb referring to a gameplay action (e.g. "to storm
  off", "then storm them some", "to wish for Tendrils").

*** Terminology

To make maintenance and refactoring easier, in-game slang and terminology should
be written in a consistent manner. Update the following list as more usage comes
up.

- Use =maindeck= and =sideboard= as a single word, no hyphen. This matches how
  these terms are overwhelmingly used across the existing content and the wider
  /Magic: the Gathering/ community, including as a verb (i.e. "maindeck this
  card"). However /main/ and /side/ as bare adjectives or shortened verbs (i.e.
  "side in the black cards against tempo") are acceptable.

*** Custom Directives

A number of custom directives are parsed within Markdown content. This allows
more features than what Markdown already supports by default. Visit =/markdown=
anywhere the Wiki is hosted to see what it actually looks like. For the
technicalities, see the supported specifications for
[[https://talk.commonmark.org/t/generic-directives-plugins-syntax/444][directives]].

The guidelines assume that the reader knows the differences between /inline/,
/leaf/ and /container/ directives.

- Inline directives (single colon =:=) ::
  Inline markup where the text does not create a new paragraph.
- Leaf directives (double colons =::=) ::
  Create a new paragraph but accept no children within.
- Container directives (a pair of triple or more colons =:::=) ::
  Also create a new paragraph but accept children between the opening and
  closing pairs. It is possible to nest /container/ directives by using an
  increasing number of colons.

** Testing your Changes

This is a Next.js application written with TypeScript and I'll assume basic
knowledge for a JavaScript stack is known from the reader.

*** Scryfall Dependency

Scryfall recently updated their good citizenship contract requirements in terms
of rate limit. See [[https://scryfall.com/docs/api/rate-limits]].

However their real-world enforcement is stricter than that: it's a cumulative
rolling-window undocumented budget rather than a flat per-second rate, and a
build resolving hundreds of unique card references reliably exhausts it
regardless of how conservatively requests are paced, at which point every
in-flight request fails for a full 60 second lockout.

As it stands, there is a =scrydrop= dependency which acts as a local proxy for
Scryfall requests, and it now resolves those requests from a local copy of
Scryfall's own [[https://scryfall.com/docs/api/bulk-data][bulk data]] export
instead of the live API. Neither =pnpm dev= nor =pnpm build= makes any
rate-limited request to Scryfall at all: =scrydrop pull= downloads the current
bulk data export once, and =scrydrop server= resolves every query against an
in-memory index built from that file. This also means the Wiki keeps preferring
the oldest printing of a card by default without the precision tradeoff the old
batching-based approach required.

See [[https://github.com/angrybacon/scrydrop][angrybacon/scrydrop]] for more
details.

*** Running It Locally

#+BEGIN_SRC sh
pnpm install  # Install dependencies
pnpm dev      # Run the application on http://localhost:3000
#+END_SRC

See [[./package.json][package.json]] for a complete list of the available
commands.

Running the project locally ensures you abide by the existing conventions and
enables live preview for your changes. If for some reason you cannot run the
project locally, Vercel generates and updates URLs for every pull request on the
repository.

As general advice, avoid pushing for every little change you make as build
minutes are free but not infinite.
